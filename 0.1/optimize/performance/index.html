Performance

Performance

Timings against SciPy 1.18.1, including the curve fits where SciPy is faster, and how they were taken.

You are reading the documentation of an outdated version, whose text may no longer be accurate. Go to the latest version.

Method

The benchmarks pair bench_test.go with benchmarks/bench_scipy.py, which runs the same problems from the same starting points. benchmarks/run.sh alternates the two: each round runs every Go benchmark once (-benchtime=300ms), then the whole SciPy script (each case a median of 3 batches of at least 0.2 s). Interleaving spreads the load changes of a shared host evenly over both sides. benchmarks/summarize.py reports the median over rounds. The raw numbers are in benchmarks/results.json.

Setup of the run below:

  • 7 rounds on 2026-10-10 on an Apple Silicon (arm64) Mac, Go 1.27.2, SciPy 1.18.1, NumPy 2.5.4, CPython 3.12.
  • The host is shared: the load average was 13–19 during the run (60+ earlier that day). Absolute times are therefore pessimistic for both sides, and ratios move by about ±20% from run to run.
  • The SciPy objectives are SciPy’s own vectorised rosen/rosen_der, and the curve-fit model is a vectorised NumPy expression. That is the fastest form a notebook would write, not a straw man.

How to read the columns:

  • “SciPy time in Python callbacks” is the time to make SciPy’s own nfev objective calls and njev gradient calls, outside the optimiser.
  • The last column divides SciPy’s time minus those callbacks by ours. It is the honest comparison of the algorithms’ own code, because Go’s callbacks cost almost nothing.

What the numbers say

  • Small problems (n = 2): SciPy’s time is almost all fixed Python overhead (argument handling, ScalarFunction wrappers, NumPy calls on 2-element arrays) plus about 10 µs per callback. Go spends nanoseconds on each. The gap is 100–450× and stays above 85× even after crediting SciPy with free callbacks.
  • BFGS at n = 100: our update is O(n²) where SciPy does two dense n×n matrix products per iteration. That is the 5× left once SciPy’s callbacks are removed.
  • L-BFGS-B at n = 100: SciPy’s core is compiled C with BLAS, and ours is Go. With callbacks counted we are 3.7× faster. Without them the cores are within 2× of each other, ours ahead.
  • Finite differences: each forward-difference gradient costs n Python calls in SciPy and n inlined Go calls here. At n = 100 that is 73×.
  • curve_fit with 10⁴ points: SciPy is faster here, and we say so.
    • SciPy’s model call is one vectorised NumPy expression per evaluation, so it pays no per-point Python overhead. Its MINPACK and LAPACK kernels are compiled C.
    • Our per-point model evaluation is at parity with NumPy: 58 µs against 56 µs per sweep of 10⁴ exponentials, measured separately.
    • The remaining gap is the solver itself on m×n = 10⁴×3 work arrays. The MINPACK port keeps MINPACK’s reference operation order and its three-accumulator norm for bit parity, and it allocates its m-sized workspace on every call.
    • CurveFitOptions.Workers (parallel model evaluation) did not change the picture: the model accounts for only about a third of the time.
    • Closing the gap means a fit-specific LM that reuses its buffers and uses blocked norms. That is not done.
  • brentq: 32×, almost entirely because the 8 callbacks are Go calls.

SLSQP

Measured with tools/slsqpbench (Go): interleaved rounds of BenchmarkSLSQP* (-test.cpu 1) and SciPy’s minimize(method='SLSQP') on the same problems with one BLAS thread; it refuses to start above a 1-minute load of 8. Apple M4 Max, SciPy 1.18.1, 2026-10-30, medians of 7 rounds, load 4.6 before and 5.4 after.

Reproducing 

benchmarks/run.sh 7          # needs uv (https://docs.astral.sh/uv/) for SciPy
GOWORK=off go test -run '^$' -bench . -benchtime=1s   # Go side only
