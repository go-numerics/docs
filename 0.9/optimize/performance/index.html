Performance

Timings against SciPy 1.18.1, including the curve fits where SciPy is faster, and how they were taken.

You are reading the documentation of an outdated version, whose text may no longer be accurate. Go to the latest version.

The harness (refbench, bench/)

bench/ is a module of its own that measures every public solver against scipy.optimize 1.18.1 with go-scikit/refbench v0.1.2: one core on both sides, interleaved rounds, gated on the 1-minute load, verdict on the median. It replaces the earlier benchmarks/bench_scipy.py harness. One row (bench/perf_test.go) is one solver call posed to both sides.

cd bench
go test -run TestPerf -cpu 1 .                   # CI: allocations, table, inventory (no Python)
go test -run TestPerf -cpu 1 -perf.run .         # measure; writes docs/perf.json, docs/perf-table.md
go test -run TestPerf -perf.record .             # allocation counts only (status: deferred)
go test -run 'TestDataParity|TestCounts' -perf.parity .   # same bytes, same nfev/nit (needs uv)

What makes a row comparable (checked, not assumed):

  • Same data. TestDataParity hashes (SHA-256) the arguments of every row on both sides. The curve-fit and LP data are read from bench/testdata/data.f64 by both sides (NumPy’s sin/exp differ from Go’s in the last bit, and an earlier version of this table generated them on each side).
  • Same starting point, same tolerances (the defaults of both).
  • Same path. TestCounts runs every row once on both sides and compares nfev and nit; an optimiser that converges in a different number of evaluations is a different computation. Results are in perf-counts.md: 40 of the 46 compared rows are equal; the six n = 100 Rosenbrock rows take different paths (counts within 11%) and are named in divergent with their reason. SciPy’s root/fsolve count two more evaluations than ours on the same path.
  • Solver overhead, not the Python objective. The SciPy objective is SciPy’s own vectorised rosen/rosen_der/rosen_hess or the cheapest NumPy expression, so its callbacks are as small as they can be; on small problems they still dominate a SciPy call (the “SciPy time in Python callbacks” column of the older table below quantifies it: 30–90%). A row on a small problem therefore times the solver plus one Python call per evaluation against the solver plus one Go call. Read such a row as an upper bound on SciPy’s solver cost.
  • Allocations. docs/perf.json records the exact allocation count per call of every case; CI fails on any difference (an increase is a regression, a decrease must be recorded). The counts are the same on every architecture where CI runs them.

docs/perf-exempt.md names the public functions without a row (result accessors, constructors, the QP solver, which SciPy does not have, and the random sources) with the reason of each.

The current timings are perf-table.md: refbench on v0.8.0, 2026-11-10, 1-minute load 4.81 to 6.91 (gate 8), one core, interleaved rounds per row, Apple M4 Max. No row is slower than SciPy. BFGS on Rosenbrock n = 100 (issue #53) is 5.62 ms against 47.1 ms (8.4×) with the default O(n²) update, which is tolerance-validated, not bit-identical to SciPy; Options.SciPyExactUpdate keeps the bit-exact path. The tables further down are older (2026-10-17, the earlier script) and are kept for the history of the changes they describe.

curve_fit on 10⁴ points: the model call (2026-11-09)

What the rows compared. Same data (SHA-256, TestDataParity), same p0, the default tolerances of both, the same forward-difference Jacobian (MINPACK fdjac2 with epsfcn = machine ε for LM, 2-point with step √ε for TRF, one model sweep per parameter) and the same counts (21 evaluations for LM, 6 for TRF, 8 for TRF with bounds; perf-counts.md). One thing differed: SciPy calls its model once per sweep on the whole array (a*np.exp(-b*x)+c, four vectorised NumPy passes), while CurveFit takes a scalar model and calls it once per sample, 10⁴ Go calls of a closure that calls math.Exp.

Where the time went (pprof, BenchmarkCurveFit1e4LM/TRF, one core): the model sweeps were 65% of LM and 54% of TRF. The solver (MINPACK’s qrfac/lmpar/enorm in their original order of operations, TRF’s householderR and 3×3 SVD) was the rest, with 10% of TRF in allocation and garbage collection, mostly the SVD through go-ndarray (issue #47).

The fix: Model.Vec. A model can now be given over arrays, Vec(xs, p, out), called once per sweep as SciPy calls f(xdata, *p), so it can use vector kernels: the new CurveFitVec/* rows write the NumPy expression as three passes with go-simd/floats’ Exp (about 1.35 ns per element on the M4 Max, against 2.7 ns for math.Exp and 3.2 ns per sample for the closure). Each evaluation of the residuals also stopped allocating (a closure per call, which escaped through the Workers goroutines): allocations per call went from 42 to 24 (LM), 443 to 422 (TRF), 607 to 578 (TRF with bounds) and 33 to 26 (CurveFitModel with a Jacobian). TestCurveFitEvaluationAllocs holds the count independent of the number of evaluations.

Exactness. The solvers are unchanged: with the same arithmetic per sample, Vec and F give the same fit to the last bit (TestCurveFitVecSameBits on every SciPy fixture, 1-D and (2, m) xdata, sigma, bounds, both methods, and with Workers). The vector Exp is a 0.511-ULP exp, not NumPy’s bits nor math.Exp’s, so the CurveFitVec rows agree with SciPy within the fixture tolerance (1e-6 relative on popt), as the scalar rows always did, and take the same 21 / 6 / 8 evaluations.

Provenance of perf.json and perf-table.md: they are the refbench run of 2026-11-10 at commit 6ea6138 (load 4.8-6.9), unchanged except one hand edit made in the MINPACK change: the allocation count of Root/hybr/broyden100, 25 → 15, because TestPerf checks allocations against the current code (Root n = 100 now takes the default kernels). No reordered kernel was introduced: both changes keep the reference’s bits. floats stubs lacked //go:noescape, so these calls first moved callers' work vectors to the heap (BFGS n = 2: 14 → 17 allocations); fixed in go-simd/floats v0.12.1 (TestKernelsKeepCallerSlicesOnStack), which also takes trust-constr on Rosenbrock n = 2 from 1121 to 862 allocations per call (its floats.Dot/Axpy work vectors now stay on the stack).

BFGS n = 100 (issue #53). SciPy’s two n×n products go to BLAS dgemm (46.4 ms for the 544 iterations). Bit for bit (Options.SciPyExactUpdate) ours took 172 ms on AxpyNoFMA (refbench, v0.7.1), then about 90 ms on floats.AxpyRowsNoFMA (go-simd/floats v0.13.0: a row of c stays in registers across all k, same bits; go test -bench, loaded host). That is about 27 Gflop/s, close to NEON multiply/add throughput, and no term of the sums can be skipped (A1 = I − ρ s yᵀ and A2 are dense), so the bit-exact path cannot reach SciPy’s time on one core. The default is therefore the O(n²) rank-two update, H − ρ(s uᵀ + u sᵀ) + (ρ² yᵀu + ρ) s sᵀ with u = H y, on the FMA kernels Dot and Axpy, upper triangle mirrored so H stays exactly symmetric: tolerance-validated, not bit-identical to SciPy (542 against 544 iterations at n = 100; TestBFGSDefaultUpdateAgainstExact). About 6–12 ms per call at n = 100 under load (go test -bench, indicative). Refbench v0.8.0 (2026-11-10, load below 8): 5.62 ms against SciPy’s 47.1 ms (8.4×). CG n = 100 1.26 ms against 51.2 ms; L-BFGS-B n = 100 4.75 ms against 12.1 ms.

Method of the earlier timings below

The tables below were taken with bench_test.go and a Python script that has since been replaced by bench/: each round ran every Go benchmark once (-benchtime=300ms, one thread, -test.cpu 1), then the whole SciPy script (each case a median of 3 batches of at least 0.2 s), alternating the two.

Setup of the run below:

  • 5 rounds on 2026-10-17 on an Apple M4 Max (arm64), Go 1.27.2, SciPy 1.18.1, NumPy 2.5.4 (both pinned by run.sh), CPython 3.12.
  • The host is shared: the load average was 11–13 during the run (16 cores). Ratios move by about ±10–20% from run to run.
  • The SciPy objectives are SciPy’s own vectorised rosen/rosen_der, and the curve-fit model is a vectorised NumPy expression. That is the fastest form a notebook would write, not a straw man.

How to read the columns:

  • “SciPy time in Python callbacks” is the time to make SciPy’s own nfev objective calls and njev gradient calls, outside the optimiser.
  • The last column divides SciPy’s time minus those callbacks by ours. It is the honest comparison of the algorithms’ own code, because Go’s callbacks cost almost nothing.
  • linprog: SciPy 1.18 only has HiGHS; this package has a revised simplex and the interior-point method SciPy used to have. The rows compare the same LP solved to optimality, not the same algorithm.

Every operation is at least as fast as SciPy. The closest are the large least-squares problems, where SciPy’s model and its kernels are compiled code; they are discussed below.

Same iterations as SciPy

The slow rows were not doing more work: Go and SciPy take the same steps (curve_fit LM: 21 function evaluations each, TRF: 6 Jacobians, bounded TRF: 8; root on Broyden: 111 evaluations plus SciPy’s 2 wrapper calls). The time went into the per-iteration linear algebra.

What changed

All of it keeps every sum in its original order, so every result is unchanged to the last bit (see “Evidence” below).

  • Independent sums advance in the same pass. MINPACK’s QR factorisation (qrfac) forms, one after the other, sums that do not depend on one another: the column norms, and at each step the products of the Householder vector with every remaining column. Each such sum is latency-bound (one floating-point add per element, waiting for the previous one). They are now accumulated side by side, four per pass, each in its own order. The same applies to Qᵀ·fvec, which lmdif and hybrd formed after the factorisation and which is now formed with it; to the norm of the next pivot column, accumulated while the update produces it; to the exchange of the pivot column, done in the scaling pass; to qform’s columns; to hybrd’s Broyden update and predicted reduction and dogleg’s R·g (four rows of a packed triangle at a time); and to TRF’s householderR (vᵀv with every vᵀc, the next column’s norm with the update). On 10⁴×3, qrfac went from about 100 µs to 55 µs and householderR from 162 µs to 67 µs; on 100×100, qform from 347 µs to 144 µs.
  • One range test for four components. The column norms use MINPACK’s three-accumulator enorm; testing the four components of a row for the intermediate range is one unsigned comparison of their bit patterns.
  • Fewer allocations and copies. TRF keeps its work buffers between iterations, curve_fit reads xdata and ydata in place and calls a scalar model directly instead of through a k-vector wrapper, and finiteness tests read exponent bits.
  • Small problems keep MINPACK’s plain loops. Below 32 rows the bookkeeping of the fused passes costs more than it saves (it had made root on 2 equations 5–10% slower), so qrfac, qform and the packed sums take the original loops there. Both paths give the same bits.

Evidence that results are unchanged

  • A dump of every result of curve_fit (10 option sets on 4 data sizes, with and without sigma, bounds, robust losses, 2-D xdata, analytic and numerical Jacobians), leastsq, least_squares and root on all MINPACK test problems is identical, bit for bit, before and after, on arm64 (with fused multiply-add) and on amd64 (without).
  • minpack_fused_test.go compares every fused kernel with the original code on random matrices covering every magnitude range of enorm, its exact bounds, zero and repeated columns, NaN and signed zeros: 4320 QR factorisations, 350 householderR factorisations, qform, packedRowDots, and root on 40 equations through both paths. Mutations of the fused code (a dropped term, a shifted bound) make them fail.
  • The SciPy fixture tests (bit-exact on MINPACK’s iterates and counts where they were before) pass unchanged; no tolerance was changed.

What remains close, and why

curve_fit LM is 1.07× and TRF 1.27×. Of LM’s 1.37 ms, about 0.95 ms is the 21 evaluations of the model over 10⁴ points: a Go closure calling math.Exp costs about 45 µs per sweep, against 29 µs for NumPy’s vectorised a*np.exp(-b*x)+c. The solver itself now takes about 0.4 ms against about 0.8 ms for SciPy’s compiled MINPACK and wrappers; what is left of it is the cost of the QR passes over 10⁴ rows, which the default now runs on go-simd FMA kernels (the sums are no longer sequential; the solution is within 1e-6 of the exact optimum on problems of 32 to 300 rows, TestAccuracyBoundMinpackFast). CurveFitOptions.Workers evaluates the model in parallel when that is acceptable; the table is single-threaded.

root on 100 equations is 1.27×: SciPy’s 0.83 ms is about 0.31 ms of Python callbacks and 0.5 ms of compiled MINPACK, ours 0.6 ms of solver.

SLSQP

Measured with tools/slsqpbench (Go), which builds the test binary, runs BenchmarkSLSQP* with -test.cpu 1 and SciPy’s minimize(method='SLSQP') on the same problems with one BLAS thread, in interleaved rounds, and refuses to start when the 1-minute load average is above 8. On the larger problems (dense n ≥ 500, portfolio k ≥ 10) ADMM is faster than OSQP, by up to 2× on the dense ones. The solve phase of the sparse problems is 1.04–1.49× OSQP’s and the setup 2.2–4.9×. The cause is go-sparse, not the ADMM code: the LDLᵀ solves alone (Permuted.Solve: permute, L, D, Lᵀ, un-permute) take 29–73% of our solve phase, e.g. 1.0 ms of the 2.07 ms of huber-n5, where OSQP’s complete solve phase (QDLDL solves included) is 1.39 ms; and AMD plus the symbolic analysis are 17–80% of our setup and 70% of the bytes a setup allocates (order.symGraph 23%, order.newEngine 14%, ldl.NewPermuted 20%: 140 KB for the 75×75 KKT matrix of eq-qp-n50), so that on macOS the Go runtime spends more time in GC and madvise than in the ordering. What belongs to this package was fixed in this round: loops without bounds checks in the ADMM step (huber-n5 solve 1.70 → 1.47 ms), one allocation for the rows of the model.

Open defects

  • ADMM setup 2.2–4.9× OSQP’s, solve 1.04–1.49× on sparse problems below n + m ≈ 2000 (21 of the 25 ADMM rows are flagged slower by the tool; the other four are the largest problems): go-sparse. order.AMD and ldl.NewPermuted allocate heavily (symGraph per node slices), Permuted.Solve costs about one whole OSQP iteration, and Refactor is the known 11–21% behind QDLDL. They are owned by go-sparse/sparse and are not worked around here; suggested there: a reusable workspace for AMD and the symbolic phase, the permutation fused into the first and last triangular sweep, allocation-free solves. Re-measure with tools/qpbench after each go-sparse release. (An issue could not be opened from this work; this paragraph is its text.)
  • Active set 2.0× quadprog at n = 50 and 4.6× at n = 10 (7.98 vs 1.75 µs, 263 µs vs 134 µs): the per-call setup (Cholesky of P, J = L⁻ᵀ, canonical rows, result assembly with the LPDual blocks and the from-scratch KKT residuals) is fixed cost that quadprog does not pay; at n = 200 the gap is 9% and from n = 500 we are faster. Not yet profiled below 1 ms.
  • ADMM setup allocations (about 390 KB for a 75-dimensional problem) are mostly go-sparse; ours (the model, admm.alloc, buildKKT) are about a quarter.
  • Not measured: the Maros–Mészáros medium and full tiers (they need the MAT conversion for 138 problems, qporacle mm, and a harness mode that reads them), OSQP at ε = 1e-5, and polishing.
